# Edge cases coverage in test_data.csv

Run `cargo run -- examples/test_data.csv > result.csv`, then
`diff -u examples/test_data.expected.csv result.csv`. A successful run exits zero; an empty
diff means the report matches the independently calculated balances. The expected file is a
checked-in oracle, not output regenerated by the engine.

The fixture contains 42 chronological transactions across 10 clients: 31 accepted and 11
rejected. Deposit and withdrawal IDs are globally unique; partner actions reuse the ID of
the transaction they reference. All amounts use zero through four decimal places.

| Client | TASK.md cases | Expected final account |
|---|---|---|
| 1 | Deposits increase available and total; a successful withdrawal decreases both. | `1 + 2 - 1.5 = 1.5` available and total; no hold; open. |
| 2 | Insufficient funds leave the account unchanged. Arrives before client 1. | Deposit `2`; withdrawal `3` rejected; available and total `2`; open. |
| 3 | Four-place arithmetic; dispute decreases available, increases held, preserves total; held funds cannot be withdrawn. | `10.1234 + 2 - 0.1234 = 12` total; `10.1234` held; `1.8766` available; withdrawal `2` rejected. |
| 4 | Resolve releases a disputed amount, restores available, preserves total. | `7.8901` restored, then `0.0001` withdrawn; available and total `7.89`; no hold; open. |
| 5 | Chargeback removes held funds and decreases total; account freezes immediately. | Charge back `8.25`, leaving the other deposit of `2`; subsequent deposit and withdrawal rejected; locked. |
| 6 | Fraud example: deposit, withdraw, reverse the original deposit. | `10 - 10 - 10 = -10` available and total; no hold; locked. Negative balances follow the README's documented interpretation. |
| 7 | Unknown dispute, resolve and chargeback IDs are ignored; resolve and chargeback without a dispute are ignored; subsequent valid rows still run. | All five partner errors leave `4.5678` unchanged; withdrawal `0.5678` leaves `4`; open. |
| 8 | A resolved deposit is no longer disputed: subsequent resolve/chargeback are ignored. Re-dispute and chargeback exercise the documented lifecycle. | `5` restored, disputed again, then charged back; zero balances; locked. |
| 0 | Valid lower ID bounds (`u16` client 0, `u32` transaction 0), withdrawal of exactly all available funds. | Deposit and withdrawal of `0.0001`; zero balances; open. |
| 65535 | Valid upper ID bounds (`u16::MAX`, `u32::MAX`), surrounding whitespace and four-place precision. | `123.4567 - 0.0001 = 123.4566` available and total; no hold; open. |

Across the file, client and transaction IDs are deliberately unsorted. Dispute, resolve and
chargeback rows use both an empty fourth field and an omitted fourth field. The `csv` reader
accepts those varying record lengths; transaction validation still requires an amount for
deposits and withdrawals. Whitespace surrounds header names and values, including a quoted
amount field. Final output checks the required five columns, decimal values and lock flags.

`tests/task_cases.rs` checks each row against explicit intermediate balances and acceptance
decisions, including `total == available + held`. `tests/cli.rs` runs the real binary and
compares its entire stdout with `examples/test_data.expected.csv`. Large-input resource usage
needs separate benchmarks.
